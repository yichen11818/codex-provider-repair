# 结果解释与恢复边界

## 先看报告

`summary.database_rows`、`affected_files`、`metadata_changes` 是本次参数选中的候选修改数量；应用后的结果报告仍保留该批修改前清单。用单独的后续预览报告判断剩余数量。

| `issues[].kind` | 含义和处理 |
| --- | --- |
| `provider_not_configured` | 会话/DB 引用的供应商未出现在指定主目录全局配置或内置集合中；排除项目/profile 覆盖后可按目标迁移 |
| `active_provider_not_configured` | 全局当前供应商本身没有定义；不能通过迁移历史到这个无效目标解决 |
| `db_session_provider_mismatch` | DB 记录与文件最后一条 `session_meta` 的非空供应商不同；不要声称最后一条就是所有 Codex 版本的权威读取来源 |
| `database_provider_mismatch` | 同一会话在不同状态 DB 中供应商不同；同时检查两处，不硬编码哪处必然生效 |
| `multiple_metadata_providers` | 一个文件的多条 `session_meta` 使用不同供应商，可能来自迁移或历史追加；缺失引用可修，其他差异需结合用户迁移目标 |
| `rollout_path_not_scanned` | DB 保存路径不在本次已扫描集合，可能已归档移动、文件缺失或超出允许目录；`found_by_id` 给出按元数据 ID 找到的候选，不自动修路径或删 DB 行 |
| `missing_session_meta` | 文件未找到可解析的会话元数据；不伪造记录 |
| `no_state_database_found` / `no_session_files_found` | 对应检查面没有发现数据；不要据此宣称健康 |
| `thread_not_found` | 限定会话未在 DB 或元数据找到；核对本机/远端和主目录 |

默认目标是当前全局供应商；审计可以检查未配置的目标，执行修复必须使用已配置目标。只报告配置解析错误时，应先定位实际 TOML 问题，不删除 `config.toml`，也不猜测 API 地址或凭据。

进程退出码 `0` 表示检查或指定操作完成，不等于无问题；`2` 通常表示参数/配置或扫描错误。修复中途异常可能已完成部分独立文件或数据库事务，查 `status`、各项 `status` 和 `apply_error`。不能把整批跨文件操作描述为一个原子事务。

## 数据保留

报告仅包含路径、会话 ID、供应商、计数及散列，不复制聊天正文、配置内容或密钥。备份文件本身是完整原始聊天历史/数据库，只保存在本机备份目录，不打包进 skill、不输出数据库标题/正文做无关展示。

脚本不会自动改有效供应商间的不一致。用户指定来源和目标时，可使用重复的 `--from-provider` 并结合 `--thread-id` 限定范围；不要用 `WHERE model_provider != 'custom'` 无差别迁移。

## 用户要求回退时

1. 找到该次 `manifest.json`，核对 `home`、原供应商、受影响文件、数据库和执行状态。
2. 停止相关会话写入后才安排恢复。当前技能不会自动关闭应用。
3. 文件恢复前比较当前 SHA-256 与清单 `new_sha256`。匹配才可用其原始备份恢复；不匹配说明修复后又有变动，应只做字段级回退并保留新增聊天。
4. 优先依据清单按会话 ID、当前目标供应商进行数据库字段级回退，避免恢复整个旧快照而丢失后来数据。回退本身也要备份并使用事务。
5. 全库快照恢复只在明确需要且 Codex 已退出时进行；还必须正确处理现有 WAL/SHM，不能直接在运行中的 DB 上拷贝 `.sqlite` 文件。

恢复不是检测流程的自动步骤。若无法判断修复后的新增数据，应保留现状，先向用户说明具体冲突。
